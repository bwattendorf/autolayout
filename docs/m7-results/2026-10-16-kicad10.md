# KiCad 10 (2026-10-16): format support and a grader comparison

KiCad 10.0.6 installed beside 9.0.1 (`C:\Program Files\KiCad\10.0` and `...\9.0`; installer from the official release URL, SHA256 checked against the winget manifest, run by the owner because a silent install exited 666660 with no message, cause not found). `kicad-cli version`: 9.0.1 and 10.0.6. All numbers measured, one run per board, `tools/m7_batch.py`, `AUTOLAYOUT_CORPUS=C:/Portcullis/controller/boards`.

## Format change found
A board saved by KiCad 10 has `(version 20260206)` (KiCad 9: 20241229) and refers to nets **by name**: no top-level `(net N "name")` table, no net 0 entry, and `(net "GND")` on pads, tracks, vias and zones (measured on `b_prepared.kicad_pcb` and on a v9 routed board re-saved by KiCad 10's pcbnew: 1911 references, all `(net "S")`). Our reader and writer assumed numeric codes. First trial (`out/k10_one`, m1/candidate4 through the old pipeline): `FAIL:route ... plane net GND is not a net of this board`.
The format document at dev-docs.kicad.org was not checked for the new style; it is known from real files only.

## What changed in our code
- `board::NetTable` / `Board::net_table`: a file with no top-level net table and `(net "name")` references is name-style; the distinct names, sorted, get made-up codes 1..n (0 is no net). `NetTable::code_of(item)` reads the net of a pad, track, via, arc or zone in either style. Codes are internal only and never written.
- `route::model`, `route::verify` read nets through `code_of`; `route::write` writes `(net "name")` (escaped) for a name-style board and `(net N)` otherwise. Output bytes for KiCad 9 boards are unchanged (the uuid keys still use the code).
- Tests: `net_style_tests` (board) and `name_style_board_routes_and_writes_nets_by_name` (route). `ci.sh` exit 0 with the KiCad cross-check.

## Checks
- `autolayout verify` on the same routed board in KiCad 9 format and as re-saved by KiCad 10: both 993 segments, 419 vias, unconnected 10, clearance 1.
- Whole pipeline on KiCad 10 (pour and refill with 10's pcbnew, DRC with 10's kicad-cli, our router on the v10 file, v10 output) on m1/candidate4: runs end to end; written file is v10 with `(net "...")`; our verifier (20 unconnected, 1 clearance) agrees with KiCad 10 (20 unconnected). It routes to 84/99 nets, KiCad unconnected **20**, against 10 on the KiCad 9 path, because the made-up codes change the order nets are tried in; that board is known to swing by about 10 on small changes. Not a regression of the router, not examined further. Only this one board was run on the all-KiCad-10 pipeline.

## KiCad 10 as the grader on our existing copper (`out/m7r26_k10drc`, 37 boards)
Pour/refill with KiCad 9 python (so the files stay v9), DRC with KiCad 10.0.6, router of commit `babf09a` (identical copper to Round 25), against Round 25 (`out/m7r25_all`, KiCad 9.0.1):
| metric | KiCad 9.0.1 | KiCad 10.0.6 |
|---|---|---|
| unconnected after / before routing | 125 / 14947 | 125 / 14947 |
| hole-to-hole, dangling, track width, copper edge, hole clearance | 4 / 0 / 0 / 0 / 0 | 4 / 0 / 0 / 0 / 0 |
| clearance, raw report lines | 122 | 485 |
| shorting, raw report lines | 5 | 11 |
| clearance / shorting counted once per item pair | 122 / 5 | 122 / 5 |
KiCad 10 lists a pad-to-pad violation once per copper layer it spans (the J10 through-hole pad pairs on 4-layer boards: 14 became 56 on the m1 boards), so the raw count is about 4 times higher on 10 boards. Counted once per pair of items it is the same 122 and 5. So KiCad 10.0.6 gives the same verdict as 9.0.1 on every board; `tools/m7_batch.py` still reports the raw count (not changed here).
